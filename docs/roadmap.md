# 今後の検討

現行仕様に含まれない機能と、導入時に改めて設計する事項をまとめる。実装時には、機微な情報を扱うことと、本人を評価・監視しないというプロダクト方針を優先する。

## 招待と複数の共有スペース

- アプリ内の招待と Cloudflare Access の許可をどう連携するか。
- 複数グループを導入する場合のグループ・所属テーブルと、カテゴリ・記録の移行方法。既存の利用者を自動で参加させず、運用者が確認する。
- 記録対象者を区別する場合のテーブルと記録との関連。既存記録には対象者 ID がないため、後からの自動分類は行わず、必要なら手動で確認する。

## AI による文章の整形

AI を導入する場合も、役割は親族が書いた文章を読み返しやすく整えることに限る。診断、病名、認知症の可能性、医学的な意味付け、評価、傾向分析は行わない。

- 原文を入力し、整形結果をプレビューして、利用者が確認・修正してから保存する。
- 原文にない事実を足さず、「異常」「問題」「悪化」のような判定を含む言葉を使わない。
- 原文は保存するが、一覧と詳細には出さない。整形に失敗したときは、原文を確認画面に出してそのまま、または手で直して保存できるようにする。
- 接続先は OpenAI 互換 API とし、ローカル LLM を既定にする。外部 API を使う場合は、利用者が選べるようにする。
- LLM を呼んでいる間は DB トランザクションを開かず、LLM が使えなくても記録を保存できるようにする。
- 原文を保存するための `entries.raw_text` を追加する。

## その他

- 通知、画像・音声の添付、アカウント削除、権限の細分化
- 一覧のページ送り。期間で絞り込んでも件数が多くなった場合に検討する。
- Cloudflare Access のメール変更・IdP変更時の `sub` の振る舞いと、本人確認・引き継ぎの運用手順
- 複数の認証発行元を扱う場合の、発行元と `sub` を組み合わせた識別方法
