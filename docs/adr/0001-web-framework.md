# ADR 0001: Web フレームワークに SvelteKit を採用する

- 状態: 採用済み
- 日付: 2026-10-26

## 背景

みんなのきろくは、家族内で共有する機微な記録を扱う Web アプリである。自宅サーバー上の Docker で動かし、Cloudflare Access で認証する。サーバー側の認証・権限確認、HTML フォーム、SQLite を使った小規模な構成を、過剰な構成にせず保守できる必要がある。

## 判断基準

- TypeScript で画面とサーバー側の処理を実装できること
- サーバー専用コードを明確に分離できること
- JavaScript が使えない環境でもフォーム操作を提供しやすいこと
- Node.js と Docker で単体のアプリケーションとして運用できること
- 依存関係を少なく保ち、継続的に更新できること

## 決定

SvelteKit と `@sveltejs/adapter-node` を採用する。認証、DB 操作、権限確認は `src/lib/server/` とサーバー側のルートに置き、ブラウザ側へ公開しない。画面の更新は Svelte を使うが、記録の作成・編集・削除は通常の HTML フォームでも動作させる。

## 検討した選択肢

| 選択肢 | 判断 |
|---|---|
| SvelteKit（`adapter-node`） | 採用。必要な画面・サーバー処理を一つの TypeScript プロジェクトで扱える。 |
| Next.js（App Router） | 見送り。このアプリの規模では必要な機能に対して構成が大きい。 |
| Hono / Fastify と別のフロントエンド | 見送り。画面・ルーティング・フォーム・CSRF 対策を別々に組み立てる必要がある。 |
| React Router のフレームワークモード | 見送り。React を採用する固有の要件がない。 |

## 結果

- Node.js の依存関係と SvelteKit のセキュリティ更新を継続して適用する。
- フレームワークの脆弱性情報は、特定製品との件数比較ではなく、公式の更新情報と影響範囲に基づいて判断する。
- 複数コンテナへの水平分割や、より複雑な認証要件が必要になった場合は、この判断を見直す。
